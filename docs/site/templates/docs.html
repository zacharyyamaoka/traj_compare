Pick a pair and call compare(reference, measured). You get the error as a trajectory of the same type, reference − measured on the measured run's own samples, an ErrorStats per joint, axis and channel, and a record of how the two clocks were lined up. check turns that into a ROS 2 verdict; traj_compare draws it as an offline report and a Rerun file.

How it works#

Two packages, split at one line: the maths in a library you can call from anywhere, the pictures in a viewer that only reads its results.

  • robot_msgs.compare is the library. Pure numpy, like the rest of robot_msgs, so it runs in a notebook, a test or a controller loop. One generic function dispatched on the trajectory type, plus a one-line method: target.compare(real) is compare(target, real).[[n:code_design]]
  • traj_compare is the viewer. You hand it runs as arrays (Situation: t, q, qd, qdd, tau, current, poses, video) and an fk. It calls robot_msgs.compare for every error and statistic and never computes one itself, then writes report.html and, with rerun=True, one .rrd per page.[[n:code_viewer]]

What compare returns, robot_msgs.compare.Comparison:

FieldWhat it holds
errorA trajectory of the same type as the inputs (JointTrajectory or PoseTrajectory), reference − measured, on the measured run's samples inside the reference. A pose error also carries channels: rotation_vector, rotation_angle, lag, cross_track, contour, lag_time.
metricsStable name → ErrorStats (metric names, fields). rows() gives them as tidy rows for a table.
time_offset_sThe offset applied to the measured clock: how late it runs.
droppedMeasured samples outside the reference's span, so not compared.
coverageFraction of the reference's duration the measured run covers.

Same word, two objects. robot_msgs.compare.Comparison is the result above. traj_compare.Comparison is the page you hand the viewer: a reference (its target field), the runs to overlay, an fk and display options.

The rules#

Each rule is in the code; each has a reason.

  1. error = reference − measured.

    It is the ROS 2 JointTrajectoryControllerState convention, and the controller computes it the same way.[[n:jtc_state,jtc_cpp]] A positive error is the correction still to apply, and a positive lag means the run is behind.

  2. Errors are taken on the measured run's own samples.

    Never on a shared resampled grid: a 1 kHz joint's ringing disappears on a 100 Hz grid. The reference is interpolated at the measured instants, which is safe because a commanded reference is dense.[[n:code_align]]

  3. Never extrapolate. Measured samples outside the reference are dropped and counted (dropped), and coverage says how much of the reference was measured.

    An error against a frozen last value is invented, not observed. And without coverage, a run covering 60 % and one covering 100 % report RMS over different windows with no warning.[[n:code_align,matlab_sdi]]

  4. One clock; latency is explicit. Both runs sit on header.stamp + t. A known latency is time_offset_s (how late the measured clock runs), passed by you, never guessed.

    An offset applied silently is a decision hidden inside a number. estimate_time_offset measures it; you decide to apply it.

  5. Same type in, same type out.

    The error of two JointTrajectorys is a JointTrajectory, so every plot, resampler, slicer and serialiser already works on it. No parallel “error” schema.[[n:code_design]]

  6. Pairwise on purpose. N runs is a loop. N repeats of one reference is aggregate. Sim → real has no target.

    Every SLAM evaluator keeps compare pairwise.[[n:evo,rpg,evalio]] Widening it would hide which run was the reference.

  7. Cartesian is built outside. Make a PoseTrajectory per point you care about with your FK, name it in child_frame_id, and compare those: PoseTrajectory.from_matrices(t, fk(q), child_frame_id="TCP").

    The right point differs per robot (a 6-DOF TCP, a five-bar's L2 tip or coupler point), and the library owns no kinematics.

  8. Every decision travels with the numbers.

    time_offset_s, dropped and coverage sit beside error and metrics, and a Comparison round-trips through JSON / npz like any message. A number separated from how it was made cannot be checked later.[[n:code_design]]

  9. Metric names are stable strings.

    positions/<joint>, position, lag, channels/<name>…: adding a metric never changes a type.

Target → sim, target → real, sim → real#

Three questions, three pairs. The reference is whichever run you trust for the question; the error always reads reference − measured.

  • Target → sim: is the controller good enough in sim? Tune here first.
  • Target → real: does the robot do what we commanded? This is the one a verdict gates.
  • Sim → real: is the sim a faithful twin? No target involved: sim is the reference. If this error is small, results in sim transfer.

Cartesian: one pose per point#

Joint error says which motor; Cartesian error says what the tool did. Build a PoseTrajectory for each point you care about and compare those.

{{snippet_cartesian}}

Two ways to split the position error against a moving reference, both reported:

  • Tangent split (lag, cross_track): the error projected on the reference's direction of travel at the same instant. No search, exact on straight segments; on a curve it leaks some lag into cross-track. This is the lag / contour linearisation of model predictive contouring control.[[n:code_difference]]
  • Nearest point (contour, lag_time): the exact distance to the reference path, and how many seconds behind that nearest point the run is. Searched only within ±contour_window_s (0.25 s) of the sample's reference time, so a route that retraces itself cannot snap to its other pass.[[n:cnc_fiveaxis,cnc_thesis]]

Rotation errors are a world-frame rotation vector of q_ref · q_meas⁻¹, so rx / ry / rz are about the fixed axes. They are never a difference of Euler angles, which couple and jump at gimbal lock.

The conveyor frame#

A belt pick cares about errors along and across the belt, and whether the tool holds belt speed. Two options on the page say which directions matter.

  • vec_dirs=[("Conveyor", direction)] adds Path-progress channels Vec[Conveyor]: signed progress, speed (_d) and acceleration along that direction. Belt-speed matching reads straight off Vec[Conveyor]_d: on the track segment it must sit flat at belt speed (0.35 m/s in the UR5e example). A plateau at the wrong height means the tool slips against the part; a sloped one means it is still accelerating.
  • error_axes=[("along belt", b), ("across belt", b × up), ("up", up)] projects the TCP position error (reference − run) on each direction, as extra TCP-error plots in mm and as /error/axes/… in Rerun. With the belt along world +y, “along belt” equals the world y error exactly; the viewer's test pins that to 1e-12.[[n:code_wave2_test]]
{{snippet_conveyor}}

Metrics#

Every metric is a stable string key in Comparison.metrics, valued an ErrorStats, in SI units. Which ones appear depends on the input type and on what both runs carry.[[n:code_metrics]]

ErrorStats#

The summary of one error signal, in its own unit. It is evo's statistic set plus what tracking needs on top: the worst magnitude, a p95 that ignores one glitch, the final error and the control-loop integrals.[[n:evo,sproclib]]

Verdicts#

check(reference, measured, tolerances) judges a recorded run the way ROS 2's joint_trajectory_controller judges a live one, in its vocabulary, and returns an Outcome with a FollowJointTrajectory result code.[[n:fjt_action,joint_tolerance,jtc_docs,code_tolerances]]

HereROS 2Meaning
Tolerances.pathgoal path_tolerance · JTC constraints.<joint>.trajectoryLimits at every sample while the reference runs. The first breach ends the check, as JTC aborts the goal.
Tolerances.goalgoal goal_tolerance · JTC constraints.<joint>.goalLimits once the reference has ended, judged against its final point held.
goal_time_tolerancegoal goal_time_tolerance · JTC constraints.goal_timeSeconds after the end to meet the goal. 0 here means “as long as the data lasts”; JTC's parameter defaults to 10 s and reads 0 as no grace period.[[n:jtc_params]] Pass the controller's value.
stopped_velocity_toleranceJTC constraints.stopped_velocity_toleranceDefault goal limit on every joint's |velocity| (0.01, as in JTC), used when goal has a limit and the joint sets no velocity of its own.
JointTolerance(name, position, velocity, acceleration)control_msgs/JointToleranceAbove 0 is a limit on |reference − measured|. 0 or −1 means not checked (ROS: 0 = server default, −1 = none; here a Tolerances already is the default set).
PoseTolerance(position, rotation)— (ours)Magnitude limits for a PoseTrajectory, m and rad.
Outcome.error_coderesult error_codeSUCCESSFUL {{code_successful}}, PATH_TOLERANCE_VIOLATED {{code_path}}, GOAL_TOLERANCE_VIOLATED {{code_goal}}.

Two phases, one boundary:

  • Path: measured samples inside the reference, before its end.
  • Goal: from the reference's end on (inclusive), within goal_time_tolerance if it is set, against the final point held. That is the controller's own convention, and the only place a held reference is used; it never feeds a path statistic.

The Outcome says why, not just whether:

  • violations: the first breach per (phase, metric), by time: phase, metric, t, signed error, limit.
  • margins: path/<metric> = limit − worst |error|; goal/<metric> = limit − |error| where the goal was decided. Negative = violated by that much.
  • goal_time: seconds after the end at which the goal was met (NaN if not).
  • unchecked: defaults the data could not support, such as a stopped-velocity check on a run without velocities. Never a silent pass. A limit you set explicitly with no data to check it raises instead.
  • A run that ends before the goal is observed is GOAL_TOLERANCE_VIOLATED, never a pass.
{{snippet_verdict_offline}}

Online and offline#

The same rule runs inside a controller loop, so the controller can stop the moment a tolerance breaks. ToleranceMonitor.step(t, reference_point, measured_point) returns None while undecided, then the Outcome on that tick and every later one.

{{snippet_verdict_online}}

check and ToleranceMonitor share one per-sample function and one phase boundary, so the online verdict and the offline verdict on the same samples cannot disagree. The test suite mutates that boundary and both the online and offline tests go red.[[n:code_tolerances]]

ROS's joint_trajectory_controller does its own checking with the same vocabulary.[[n:jtc_docs,jtc_params]] Given the same tolerances, an abort on the robot and the offline check of its recording report the same code; the one setting to align by hand is goal_time, whose zero means something different there.

Across N runs: accuracy vs repeatability#

Repeat a motion N times and the error has two parts with different cures. ISO 9283 separates them around the runs' barycentre.[[n:iso_hexagon,robodk,code_aggregate]]

  • Accuracy (result.accuracy): compare(reference, barycentre), a full Comparison. A bias; feed-forward or calibration can remove it.
  • Repeatability (result.repeatability, result.metrics): per instant RP = l̄ + 3·Sl, where li is run i's distance to the barycentre and Sl its sample standard deviation (ddof = 1). Joints: per joint. Poses: position and rotation. Only a better controller or a steadier plant shrinks it.
  • Every run is resampled onto the reference instants that all runs cover, never extrapolated; coverage says how much that is. Needs at least 2 runs; time_offset_s may be one per run.
{{snippet_aggregate}}

Not an average of per-sample errors across runs (evo's merge_results): per-sample errors only line up on identical timelines, and a mean of signed errors hides the spread.[[n:evo]]

The standard is paywalled; the procedure details here come from secondary summaries.[[n:iso_hexagon,iso_sample,robodk]] In the report, repeat_groups={"Real ×3": [...]} adds an ISO 9283 card per group.

Latency#

estimate_time_offset(reference, measured) measures how late the measured clock runs, from positions alone.[[n:code_timing,trajectopy,scipy_lags]]

  1. Coarse: normalised cross-correlation of the two runs' velocities on a uniform grid at the reference's median step, lags within ±max_offset_s (0.25 s).
  2. Refine: golden-section search for the offset that minimises the position RMS, over the coarse lag ± 3 steps, to 1 µs.

It returns offset_s (the sign of time_offset_s), rms_before and rms_after. If the RMS barely drops, timing was not the problem. Then feed it back, explicitly:

{{snippet_latency}}

Velocities for the coarse step, because positions of a ramp or slow drift have no sharp correlation peak. Normalised over the overlap, because a motion between rests keeps the same correlation sum as the overlap shrinks, so a per-sample mean rewards the largest lag (a 10 ms delay once read as 88 ms).[[n:code_timing]]

In the report, estimate_latency=True adds an “Est. latency” column per run.

Goal, settling, overshoot#

goal(reference, measured, band=...) looks at the samples at or after the reference's end, against its final point held (the same rule as the goal phase of a verdict), and returns a GoalStats per joint (positions/<joint>) or for a pose (position).[[n:stepinfo,python_control,code_goal]]

  • final_error: at the last measured sample.
  • settling_time: seconds after the end from which |error| ≤ band holds for every later sample. NaN if it never settles, never “the end of the data”.
  • overshoot, overshoot_percent: how far past the final value along the reference's net move, and as a percent of the move (MATLAB stepinfo's convention).
  • band: one number, or a mapping metric → band, in the signal's unit.
{{snippet_goal}}

In the report, goal_band (rad) and tcp_goal_band (m) add the “Settling · overshoot” column.

Drift: relative error over windows#

relative_error(reference, measured, delta=..., unit="s" | "m") is evo's relative pose error: for each sample i and the first sample j at least delta later (seconds, or metres of the reference's path), Eij = (Qi⁻¹Qj)⁻¹(Pi⁻¹Pj), the motion the run gained beyond the reference's own. A constant offset cancels; a drift does not. Keys: relative/<delta><unit>/position and …/rotation.[[n:evo,tum,kitti,evalio,code_goal]]

{{snippet_drift}}

Mostly for long conveyor tracking, where a slow creep along the belt hides under a large constant offset.

Shape without time: Fréchet#

frechet(reference, measured) is the discrete Fréchet distance between the two position curves (or joint-position vectors, matched by name): how far apart the paths are as shapes, whatever the timing. No alignment, no offset; orientation is not included. A run on the right path at the wrong speed scores near 0 here and badly in compare.[[n:eiter,shapely,similaritymeasures,code_goal]]

{{snippet_frechet}}

Integrals: IAE, ISE, ITAE#

Every ErrorStats carries the control-loop integral criteria, by the trapezoid rule over intervals observed at both ends:[[n:sproclib,code_metrics]]

  • iae = ∫|e| dt: total error, robust.
  • ise = ∫e² dt: punishes large errors.
  • itae = ∫(t − t₀)|e| dt: punishes errors that persist late; the one to watch for slow settling.

They are NaN when a series has no time axis, so data saved before these fields existed still loads.

The version pin

An .rrd must be opened by a viewer at least as new as the SDK that wrote it; a newer viewer migrates older files, the reverse is not promised.[[n:rerun_rrd,rerun_embed]] So one pin, RERUN_SDK_VERSION = "{{sdk}}", writes the file and names the viewer in every command: uvx --from rerun-sdk=={{sdk}} rerun <abs path>.[[n:rerun_release]]

The launcher is narrow on purpose: it opens only .rrd files inside the folder it serves, refuses absolute paths and cross-origin POSTs, and sends the CORS and private-network headers app.rerun.io needs to read a localhost file.[[n:code_viewer]] Video goes in as MP4 (H.264 or AV1, decoded by the browser's WebCodecs).[[n:rerun_video]]

Exports

With exports=True every page is also written as exports/<page name>.parquet and .mcap, linked beside “Download .rrd”. They read the same payload as the plots, so no number is recomputed. The Parquet file is tidy rows (comparison, situation, reference, channel, column, t, value) for pandas or LeRobot. The MCAP file has one JSON topic per situation and channel, /traj_compare/<situation>/<channel>, plus /traj_compare/metrics with the error statistics, for PlotJuggler or Foxglove. Both need the export extra (pyarrow, mcap).

Install and run#

Runtime dependencies: numpy and robot_msgs (itself numpy-only). The Rerun SDK is an extra, imported only when you ask for rerun=True; scipy appears only in the test extra, as the rotation oracle.[[n:code_viewer]]

Run the tests
uv run --directory ~/bam_ws/src/core/mdp/agent/actor/trajectory_generation/traj_compare --extra test --extra rerun python -m pytest -q
Write a report with its Rerun files
uv run --directory ~/bam_ws/src/core/mdp/agent/actor/trajectory_generation/traj_compare --extra rerun python examples/tracking_errors_demo.py --out /tmp/tracking_errors_demo --rerun
Serve it so Open in Rerun launches the viewer
uv run --directory ~/bam_ws/src/core/mdp/agent/actor/trajectory_generation/traj_compare python -m traj_compare.serve /tmp/tracking_errors_demo --port 8767

In code: write_comparison_report(pages, out_dir, rerun=True) (raises an ImportError naming the rerun extra when the SDK is absent), or write_rrd(page, path) for one file. This site is built by docs/site/build_site.py; its README has the commands.

Prior art#

Nobody ships this off the shelf, but each field solved one piece. We copied ideas, not code. SLAM evaluators are best at bookkeeping, robot controllers at verdicts, industrial standards at separating path from timing, shape metrics at time-free comparison. None does joint space, torque and Cartesian together, and the two closest tools (evo, trajectopy) are GPL-3.0 and bring matplotlib / pandas / scipy, while robot_msgs stays numpy-only.[[n:evo,trajectopy]]

{{prior_art}}

What we kept doing, against the field

  • No spatial alignment by default. SLAM tools align because an estimator's frame is defined only up to free degrees of freedom.[[n:rpg,zhang18]] A command is the frame.
  • Interpolating the reference at the measured instants instead of matching nearest timestamps: the field avoids inventing poses, but a dense commanded reference is exactly where interpolation is safe.[[n:evo,tum]]
  • Joint space, derivatives and effort beside Cartesian: SLAM has no actuators, controllers keep no statistics.
  • Signed per-axis error, p95 and final: evo reduces everything to norms and angles; for tuning a controller the sign and the axis are the point.[[n:evo]]

Not in yet

  • MCAP / Parquet export of a Comparison, so PlotJuggler, Foxglove and LeRobot-style datasets can overlay runs without recomputing.[[n:plotjuggler,foxglove,lerobot]]
  • MoveIt-style start-state and execution-duration checks.[[n:moveit]]
  • Time weighting: RMS over time lets dwells dominate; a moving-only or per-arc-length variant is open.

Not verified: the ISO 9283 path procedure (paywalled; secondary summaries), and the control_msgs version that renamed desired / actual to reference / feedback (the changelog does not name the fields; the current names are confirmed).[[n:iso_hexagon,control_msgs_changelog,jtc_state]]
