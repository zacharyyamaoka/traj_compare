Root cause: the tensorboard round moved the Overview onto stock Vega-Lite inside `<data-workbench>` and kept only what one
chart spec could say. The League *table*, the answer, the matrix and the per-config colour were app code in `dataset.js`
and did not survive the port. Nothing in V2's Overview is wrong as a number (the oracle below matches its 0.0363 mm / 161),
it just stopped answering.

## User outcome

Open the workbench, read in one glance which config (and which model type) tracks best, by how much, where it wins
(dataset · split · deployment), how it holds up with speed and what it costs; tick a deployment and every number recounts;
one more click is the detail (the worst targets, then a target view).

## Invariants (every variant)

- **Real rows:** `../tensorboard-2026-11-24/data/rows-runs.json` (18,507 runs of all four deployments, `build_rows.py`),
  served at `/data/` by `serve.py`; never copied into git. Model type is V2's PROPOSED mapping (`MODEL_TYPE` in
  `build_rows.py`), labelled "proposed" wherever it shows.
- **Stack:** stock data-ui `<data-workbench>` (main `1f7c004`, vendored into `vendor/` here: it has §55 and §56, which V2's
  `e8c73dc` predates) over one `.base` per variant, generated by `build_bases.py` from V2's `views.base` with only the
  `Overview` page and its views replaced. What a stock view cannot draw is a **host view** registered with data-ui's own
  `registerView` (CONTRACT §1) in `kit/overview-kit.js`: it gets the scope's kept rows through the stock pipeline
  (`update(input)`), draws in its panel only, and opens records through `host.open`. One kit, shared by all five, so the
  numbers never differ between variants; variants differ in what they put on the Overview and how it reads.
- **Aggregation, named on every figure:** a target's value for a group = the median over its runs; a group's value = the
  median over its targets ("median over targets of median over its runs", V2's and Nov 23's rule). Default x = **the fastest
  speed the filter leaves** (1× unless the rail removes it), as Nov 23's `model.top`. n = targets.
- **Colour = config**, traj_compare's 16-colour palette (`report.py` `SITUATION_PALETTE`), handed out in one stable order
  (deployment, then runs) to the configs the filter leaves, so every figure on a page agrees; a legend lists only what is
  drawn. Amber/red only for problems (the cross-deployment warning).
- **Shared scenario:** 1440 × 900, headless Chrome; the landing (no filter, 18,507 runs), then tick Deployment "UR5e +
  Conveyor PnP cell" (5,750 runs). Every hero is the landing; the walkthrough's step 2 is the tick.
- **Oracle:** `oracle.py` recomputes, in Python from the same JSON, the numbers each Overview states (the League at the
  top speed, best-in counts, matrix cells, Pareto sets) for both states; `check.cjs` reads each variant's numbers from its
  views' hooks (`el.tcOverview`) and the gate passes only when they match.

## Load-bearing axes

1. **Primary object on the landing:** a sentence + table (O1) · a model × dataset grid (O2) · headline tiles (O3) · a
   chart over speed (O4) · a chart over cost (O5).
2. **Where the detail lives:** under it on the same page (O1, O2, O4, O5) · behind a tile on its own page (O3).
3. **What the reader switches:** the dataset·split facet (O1) · the column axis (O2) · nothing, tiles open pages (O3) · the
   facet grouping (O4) · the cost axis (O5).

## Directions (allocated before building)

- **O1 The League, back, over the rail.** Nov 23's answer sentence, facet chips, the League table (rank, swatch, config with
  its deployment, n targets, tool RMS at the top speed large + ×best + log bar, sparkline vs speed, energy / jerk / stop
  error each with a sparkline, best in X of Y cells, worst targets →), then "Every dataset · split at 1×": config ×
  dataset·split heatmap, best ringed, hatched = no runs, a column click switches the table. Recomputed over whatever the
  rail leaves (all four deployments).
- **O2 Model × dataset matrix first.** Rows = model type (proposed) → its configs, nested and foldable (§56's look: one
  pitch, indents, chevrons); columns = deployment → dataset, the reader switches the column to split / speed / deployment;
  cell = median tool RMS (median over targets of each target's median over runs), log ramp, best per column ringed, roll-up
  row (each column's best) and roll-up column (each row over every column), empty = hatched "no runs". One line of answer
  above it, read off the matrix. §56 is the near-stock part; its gap (numeric cells) is named.
- **O3 Headline tiles → drill.** §55's Overview grid (`layout.open: true`): a few calm headline numbers, each tile a small
  drawing of a view that opens that view's full page: best config (and its RMS, the gap to the next), coverage (% of model
  type × dataset cells with runs), speed (how the best config's RMS grows 0.1× → 1×), worst target, runs/targets left. The
  answer first; every detail one click away; tabs grow to Overview · League · Coverage · Speed · Worst targets · Targets ·
  Runs.
- **O4 Speed is the x axis.** Small multiples per model type (switchable to per deployment) of tool RMS vs speed, one line
  per CONFIG (not per dataset), direct labels at the line ends, a legend only for what the filter left; the sweep table
  under it (config × speed, value, n, best per speed marked); its answer line names the best config at each end of the
  speed range.
- **O5 Trade-off map.** Each config one point: tool RMS (log y, accuracy) vs a cost (energy per task; switchable to jerk or
  stop error), median over targets of median over runs at the top speed, sized by n targets, faceted by deployment, the
  Pareto frontier drawn and its configs named; answers "which config is best and what does it cost".

## Prototype stop line

Every variant's Overview draws from the real rows, recounts on the rail, matches the oracle in both states, and its one
interaction works (a column click, a fold and an axis switch, a tile's Open, a facet switch, a cost switch); the drill from
the Overview reaches a target's runs. Not built: production wiring into `dataset.py`/`dataset.js`, data-ui changes (gaps
are named with the exact ask, never patched), the Targets and Runs tabs (V2's, unchanged).
