# P3 · Every tab is a saved view

**Thesis.** data-ui already has the container. One `<data-views>` over the 212 trajectory rows, with a `<data-facets>`
rail beside it, gives view tabs, `+` (Add view), Save view, a pill row, and one all-views filter that every view shares.
What data-ui lacks is a view type whose entry lays out other view entries. Add `type: panels`, and every dashboard
becomes a preset. The tabs are then data-ui's own view tabs, a reader adds a dashboard with `+` like any other view,
and the rail's filter reaches every panel, because each panel is drawn from the rows data-ui hands the dashboard. Of
the five proposals, this one asks the least of data-ui: one view type plus five small changes, each listed below.

Run it: `/home/bam/traj_compare/.venv/bin/python -m traj_compare.serve /home/bam/traj_compare/docs/proposals/dashboard-pattern-2026-11-24 --port 8843`,
then open `http://127.0.0.1:8843/p3/index.html` (full page) or `/p3/embed.html` (the host app's 1000 × 680 slot).
`coverage.base` is the whole component as text (generated by `tools/emit.mjs`; `data-ui check` reports 0 errors, and
its 14 warnings are the proposed keys and types).

## Decisions that matter

1. **A dashboard is a view entry, not a new element.** `type: panels` lives in `views:` beside the stock `table`
   preset, Trajectories. A panel is `{key, title, w, view | use, open, repeat}`. `view` is an inline view entry, drawn
   by whatever registered view has its type (data-ui's own `loadView`, `new View(host, el)`, `update(input)`). The
   input is the dashboard's: same rows, same columns, same tokens. Because of this:
   - Save view, Reset, the URL and `⋯ › Copy as .base` work on dashboards with no new code.
   - A panel's own `setView` writes into its slot of the dashboard's entry, so a joint pick is kept like any view change.
   - The filter can't diverge between tabs: there is one `el.filters`.
2. **Controls inside a dashboard are its `vars:`** (Grafana's dashboard variables). One Joint declares
   `vars: [{key: joint, values: […], value}]`. Its panels say `${joint}`, for example `group: ${joint}` and
   `cells_${joint}_q_qd`. The panels view draws the picker in that dashboard's strip only. Picking a joint is a
   `setView`, so the bar shows Reset / Save view and Save view keeps the pick. Settings that apply to the whole
   component sit behind **one gear in the bar**, read from a top-level `settings:` key.
3. **A figure is defined once and reused with `use: <dashboard>/<panel>`.** Overview's small tool views are
   `use: Tool position/tool` plus `compact: true`. **By dataset** is one panel with `repeat: dataset`: a nested
   `panels` view, drawn once per dataset the rail leaves, each over that dataset's rows, with its colour on the stripe.
   This is how datasets get compared side by side. The colour key for datasets is the series slots in
   `properties.dataset.colors`. They appear as dots in the rail, badges in the table, dots in each dashboard's strip,
   and stripes on By dataset.
4. **The embed is data-ui's bar, measured.** The settings are `views="tabs" filters="rail pills" promote="filter"`.
   In the 1000 × 680 slot with the rail open, the bar is 792 px wide and shows 4 tabs plus "2 more…". Clicking the
   bar's Filter icon folds the rail: the bar is then 1000 px and all 6 tabs show. The gear sits inside the bar: the
   bar keeps 46 px of padding for it, and bar.js's fitting reads that padding. Its popover opens at
   (915, 153)–(1215, 403), inside the slot at (220, 102)–(1222, 784). check P4 passes both at load and with the gear
   open. Below 700 px of dashboard width the panels stack, and below 980 px the strip's chips drop their names.

## Best when / loses when

- **Best when** the app is already a data-ui table. robotparts, Vibe Tracks and sim2real can grow dashboards this way
  without learning a second filter, tab or save model. One more reason it fits: Zach's "filter, then switch between
  dashboards almost" is exactly what Notion's database view tabs feel like.
- **Loses when** a dashboard needs several datasets joined (that is `<data-dashboard>`'s §17 links), or wants
  per-panel rails. Here each dashboard gets the rail's single filter (plus its own `filters:`), and panels flow on 12
  columns and cannot be dragged. A tab bar with many saved dashboards folds into "N more…" sooner than a left list
  would.

## Worth keeping in a splice

1. **`type: panels` (`js/panels.js`).** It is generic and knows nothing about coverage: `use`, `vars`, `repeat`, an
   Add panel catalog, an empty-dashboard state, and a sub-host whose `setView` writes into the panel's own entry.
   Any other proposal can mount its own dashboards with it.
2. **Save as tab, with the filter kept** (`shims.js saveWithFilter`). While a filter is set, the pill row ends in
   "Save as tab…". This saves a user view whose `filters:` is the rail's filter ANDed with the view's own. The strip
   then says "this tab keeps: …". Measured: Cell · Conveyor PnP + holdout gives the tab "Cell · Conveyor PnP ·
   holdout". With the rail cleared, that tab still shows 16 and Overview shows 212.
3. **The dashboard strip.** A subset line (all → "✓ matches analyze", checked against the payload at load; a subset →
   "re-aggregated"), the rows by dataset and split as coloured dots, the tab's own controls, and + Panel.

**The query-bar fold.** Per §47, the tabs form always folds the query box behind its Search icon. P3 keeps that, and
the always-visible text filter is the rail's stock `search` facet, "Find". Both write the same all-views filter.

**The API in five lines:**

```yaml
settings: {cmap: {type: dropdown, options: {…}, default: viridis}, reverse: {type: toggle}}   # one gear in the bar
subset: {noun: trajectory, by: [dataset, split]}                                              # every dashboard's strip
views:
  - {type: panels, name: One joint, vars: [{key: joint, values: […]}], panels: [{key: planes, w: 8, view: {type: occupancy, occupancy: {group: '${joint}', …}}}]}
  - {type: panels, name: By dataset, panels: [{key: each, repeat: dataset, view: {type: panels, panels: [{use: Overview/joints, compact: true}, …]}}]}
```

## How a second app reuses it unchanged

Take robotparts' actuator datasheets as the example. The rows are the actuators, the rail is its existing `facets:`
(brand first), and it writes `views:` with two or three `type: panels` presets. A Torque dashboard would hold a `chart`
panel of peak torque against mass, a `kpi` panel, and a `table` panel of the top ten. A Thermal dashboard would carry
`vars: [{key: duty}]`. The stock table preset stays as the last tab. No page code changes: `<data-facets>` and
`<data-views>` as today, and its panels are stock views (`chart`, `kpi`, `table`, `cards`) or its own registered ones.

Vibe Tracks works the same way: tracks are the rows, the rail is status and owner, and each dashboard (KPIs, pace,
board) is a `panels` preset whose panels are its existing `pace`, `kpi` and `kanban` view entries. With
`repeat: owner` it gets one row of panels per person. Both apps get `+ → Dashboard`, Save view, and Save as tab with
the filter kept, because those come from the element, not the app.

## Gaps

- The panels grid has no drag or resize. `w` is set in the `.base` (a reader's picks land at half width), and the
  §41 dashboard editor would be the stock part for this.
- A tab's own `filters:` shows in the strip ("this tab keeps …"), not in the pill row, and the rail's counts sit
  inside it. data-ui's Filter count does include it.
- Figures are V2's, honest but not polished (no polar pointing plot, no 3-D view). Tool positions are in each
  deployment's own cell frame, so the four datasets overlay as numbers, not as one room. The Tool position dashboard
  says so.
- On every tab, the status line ("28 of 212 rows") repeats the strip's count. data-ui's status line can't yet say
  "trajectories".
